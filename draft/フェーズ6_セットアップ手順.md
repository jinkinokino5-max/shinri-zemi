## 1. 何を採ったか（案A）

```
学生 ──投稿──→ Supabase（未公開のまま溜まる）
                      │
            代表が /review/ で確認
                      │
        Edge Function が content/*.md を GitHub にコミット
                      │
        いまも動いている GitHub Actions が再ビルド → 公開
```

**公開済みの内容の「正」は、いまも Git（`content/*.md`）です。**
Supabase にあるのは「まだ公開されていない投稿」だけ。

▸ **なぜこの形にしたか。**ロードマップ 6-A は Cloudflare Pages への移行を予定していましたが、
移行すると 8月公開のために作った経路（GitHub Pages＋自動デプロイ＋検査）を作り直すことになります。
案Aなら、**いま動いているものを1つも壊さずに投稿機能だけを足せます。**
Cloudflare への移行は、必要になった時点で改めて行えます（そのときもこの投稿機能はそのまま動きます）。

▸ **副次的な利点：**投稿が git の履歴に残ります。誰がいつ何を通したかがコミットに残るため、
代表が毎年替わっても経緯を辿れます（ロードマップ「引き継ぎ」の手3）。

| いつ | どうする |
|---|---|

▸ **公開に切り替えても、Googleの審査は要りません。**審査が必要になるのは、
Gmail本文やドライブなど「機微なスコープ」を要求する場合だけです。
ここでは名前とメールしか受け取らないので、切り替えるだけで済みます。

**③ OAuth クライアントIDを作る**

左メニュー **「APIとサービス」→「認証情報」→「＋認証情報を作成」→「OAuth クライアント ID」**。

| 項目 | 入れる値 |
|---|---|
| アプリケーションの種類 | **ウェブ アプリケーション** |
| 名前 | `supabase` など（内部用。誰にも見えません） |
| **承認済みのリダイレクト URI** | 下の1行を**そのまま**貼る |

```
https://pijlevaclmlhadwraapw.supabase.co/auth/v1/callback
```

⚠ **これはサイトのURLではありません。**Supabase のURLです。
Google → Supabase → サイト、の順に戻ってくるため、Google が知るべきなのは Supabase の住所です。

⚠ シークレットは後からも見られますが、**サイトのコードや `.env.local` には絶対に書かないでください。**

### 4-1. 🔴 自分を代表にする（あなたの作業／3のあと・1回だけ・2分）

**⚠ 先に 3 を終えて、`/submit/` から一度ログインし、表示名を登録しておいてください。**
ログインしていないと `members` に行が無いので、この操作は空振りします。

Supabase ダッシュボード → **SQL Editor** → 「New query」。

**① まず、自分の行ができているか見る**

```sql
select user_id, display_name, role, created_at from members;
```

⚠ **1行も出てこない場合は、まだログインが完了していません。**3 に戻ってください。

**② 代表にする**

```sql
update members set role = 'rep' where display_name = 'ここに①で見えた表示名';
```

**③ 変わったか確かめる**

```sql
select display_name, role from members;
```

`role` が `rep` になっていれば完了です。

⚠ **なぜ SQL でやるのか。**画面からは**自分で自分を代表にできません**。
RLS の `members_update_self` が「役割は変えられない」と定めているためです
（実際に外から試して拒否されることを確認済み）。
**最初の1人だけ**は、この仕組みの外側から入れる必要があります。
**2人目以降の役割変更は、代表になったあなたが 4-2 の SQL で行えます。**

⚠ **表示名は重複しうる**ので、同じ名前の人が増えたら `user_id` で指定してください。

```sql
update members set role = 'rep' where user_id = '（①で見えたuser_id）';
```

## 5. Edge Function

承認したときに GitHub へ書き込む部分です。**関数のデプロイ（5-3）は完了しています。**
残るのは、その関数が使うトークンの発行と登録（5-1・5-2）です。

### 5-1. 🔴 GitHub のトークンを作る（あなたの作業／5分）

https://github.com/settings/personal-access-tokens/new を直接開くのが早いです。
（辿る場合：右上のアイコン → Settings → 左下 **Developer settings** →
**Personal access tokens** → **Fine-grained tokens** → **Generate new token**）

⚠ **「Tokens (classic)」ではなく「Fine-grained tokens」を選んでください。**
classic は**あなたの全リポジトリに効いてしまいます。**fine-grained なら1つに限定できます。

| 項目 | 入れる値 | 理由 |
|---|---|---|
| Token name | `shinri-zemi-publish` | あとで見たとき何の鍵か分かるように |
| Resource owner | `jinkinokino5-max` | |
| **Expiration** | **最長でも1年**（下の⚠を読んでください） | |
| Repository access | **Only select repositories** → `shinri-zemi` | ⚠ All repositories を選ばない |
| Permissions → Repository permissions → **Contents** | **Read and write** | ファイルを書くのに必要 |
| Permissions → Repository permissions → Metadata | Read-only（**自動で付きます**） | 消せません。正常です |

⚠ **Contents 以外は「No access」のままにしてください。**
このトークンがすることは「ファイルを1〜数個コミットする」だけです。
Actions も Secrets も Administration も要りません。

**「Generate token」を押すと、`github_pat_…` で始まる文字列が1回だけ表示されます。**
⚠ **この画面を閉じると二度と見られません。**次の 5-2 を先に開いておいて、すぐ貼ってください。
失くしたら作り直すだけなので、慌てなくて大丈夫です。

#### ⚠ 有効期限について（引き継ぎの落とし穴）

**トークンが切れると、承認しても公開されなくなります。**
そのとき画面に出るのは `GitHub /repos/… → 401` という、原因の分かりにくいエラーです。

- **期限は必ずカレンダーに入れてください。**「1年後の◯月◯日：心理ゼミのGitHubトークン更新」
- 「No expiration（無期限）」も選べますが、**代表が毎年替わる団体では勧めません。**
  引き継がれないまま生き続ける鍵は、誰も管理していない鍵になります
- ⚠ **代替わりのとき、このトークンは作り直してください。**前の代表の個人アカウントに
  紐づいたままだと、その人が卒業して退会した瞬間に止まります

### 5-2. 🔴 Supabase に登録する（あなたの作業／3分）

Supabase ダッシュボード → **Edge Functions → Secrets**
（新しいUIでは **Project Settings → Edge Functions → Secrets** の場合があります。
「Secrets」または「環境変数」という名前の欄を探してください）

**「Add new secret」で、次の4つを1つずつ足します。**

| 名前 | 値 |
|---|---|
| `GITHUB_TOKEN` | 5-1 で表示された `github_pat_…` をそのまま |
| `GITHUB_REPO` | `jinkinokino5-max/shinri-zemi` |
| `GITHUB_BRANCH` | `main` |
| `REPO_SUBDIR` | `output/website` |

⚠ **`GITHUB_REPO` は URL ではありません。**`https://github.com/` を付けないでください。
`オーナー名/リポジトリ名` の形です。

⚠ **`REPO_SUBDIR` を忘れないでください。**サイトのコードは
リポジトリ直下ではなく `output/website/` にあります（2026-08-10 に移動）。
これが空だと、リポジトリの根元に `content/` を作ってしまい、**ビルドに反映されません。**

⚠ **`SUPABASE_URL` と `SUPABASE_SERVICE_ROLE_KEY` は登録しないでください。**
Supabase が自動で入れています。手で入れると二重になります。

**登録したら、反映のために関数を入れ直すのが確実です**（5-3のコマンド）。
入れ直さなくても効くことが多いのですが、効かないときの原因究明に時間を使うより早いです。
