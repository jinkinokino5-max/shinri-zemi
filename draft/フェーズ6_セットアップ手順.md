## 1. 何を採ったか（案A）

```
学生 ──投稿──→ Supabase（未公開のまま溜まる）
                      │
            代表が /review/ で確認
                      │
        Edge Function が content/*.md を GitHub にコミット
                      │
        いまも動いている GitHub Actions が再ビルド → 公開
```

**公開済みの内容の「正」は、いまも Git（`content/*.md`）です。**
Supabase にあるのは「まだ公開されていない投稿」だけ。

▸ **なぜこの形にしたか。**ロードマップ 6-A は Cloudflare Pages への移行を予定していましたが、
移行すると 8月公開のために作った経路（GitHub Pages＋自動デプロイ＋検査）を作り直すことになります。
案Aなら、**いま動いているものを1つも壊さずに投稿機能だけを足せます。**
Cloudflare への移行は、必要になった時点で改めて行えます（そのときもこの投稿機能はそのまま動きます）。

▸ **副次的な利点：**投稿が git の履歴に残ります。誰がいつ何を通したかがコミットに残るため、
代表が毎年替わっても経緯を辿れます（ロードマップ「引き継ぎ」の手3）。

## 2. Supabase プロジェクトを作る

1. https://supabase.com で新規プロジェクトを作る（無料プランで足ります）
2. リージョンは **Northeast Asia (Tokyo)** を選ぶ
3. できたら **Project Settings → API** を開き、次の2つを控える
   - Project URL
   - `anon` `public` key（← **公開してよい鍵**です）

⚠ 同じ画面にある `service_role` key は**絶対にコピーしてサイト側へ貼らないこと。**
あれは全権限を持ちます。使うのは Supabase の内部（Edge Function）だけで、そこには自動で入っています。

---

## 3. Google ログインを有効にする

**Authentication → Providers → Google** を開いて有効にします。
Google Cloud Console で OAuth クライアントID を発行し、その2つの値を貼ります。

- 承認済みリダイレクトURI：Supabase の画面に表示されているURLをそのまま貼る
- Site URL（Authentication → URL Configuration）：`http://localhost:3000` と公開URLの両方を登録する

⚠ **パスワード認証（Email）は有効にしないでください。**
ロードマップ 6-B の決定です。パスワードを持たなければ、漏れません。

## 4. テーブルを作る

**SQL Editor** で `output/website/supabase/migrations/0001_submissions.sql` の中身を
そのまま貼り付けて実行します。1回で全部できます。

作られるもの：

| | 中身 |
|---|---|
| `members` | 誰がどの役割か。表示名（⚠ 本名は保存しない） |
| `submissions` | 未公開の投稿 |
| RLS | 誰が何をできるか。**画面ではなくここが権限の実体** |
| `submissions` バケット | 承認前の写真置き場（非公開） |

### 4-1. 自分を代表にする

最初に一度だけ、あなた自身を `rep`（代表）にします。
先に `/submit/` から一度ログインして表示名を登録し、そのあと SQL Editor で：

```sql
update members set role = 'rep' where display_name = 'あなたが登録した表示名';
```

⚠ **自分で自分を代表にはできない仕組みです**（RLS が止めます）。だからここだけ SQL で行います。
以降の役割変更は、代表であるあなたが行えます。

### 4-2. 部長・運営部を登録する

```sql
-- 部長にして、担当する部活を割り当てる
update members
   set role = 'leader', club_slugs = array['dokusho']
 where display_name = '…';

-- 運営部・企画部（イベントを投稿できる）
update members set role = 'staff' where display_name = '…';
```

## 5. Edge Function を置く

承認したときに GitHub へ書き込む部分です。

### 5-1. GitHub のトークンを作る

GitHub → Settings → Developer settings → **Fine-grained personal access tokens**

| 項目 | 値 |
|---|---|
| Repository access | `jinkinokino5-max/shinri-zemi` のみ |
| Permissions | **Contents: Read and write** だけ |

⚠ **これ以外の権限を付けないこと。**このトークンがすることは「ファイルを1つ書く」だけです。

### 5-2. Supabase に登録する

**Edge Functions → Secrets** に入れます。

| 名前 | 値 |
|---|---|
| `GITHUB_TOKEN` | 5-1 で作ったトークン |
| `GITHUB_REPO` | `jinkinokino5-max/shinri-zemi` |
| `GITHUB_BRANCH` | `main` |
| `REPO_SUBDIR` | `output/website` |

### 5-3. デプロイする

```bash
cd "output/website"
npx supabase login
npx supabase link --project-ref <プロジェクトの参照ID>
npx supabase functions deploy publish
```

## 6. 手元で動かす

```bash
cd "output/website"
cp .env.example .env.local     # 2行に、2で控えた値を入れる
npm run dev
```

- 投稿画面： http://localhost:3000/submit/
- 承認画面： http://localhost:3000/review/

⚠ `NEXT_PUBLIC_` が付いた値は**ビルド時にHTMLへ埋め込まれます。**
`.env.local` を変えたら、`npm run dev` を再起動してください。

## 7. 公開サイトでも動かすとき

GitHub リポジトリの **Settings → Secrets and variables → Actions → Variables** に、
`NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_ANON_KEY` を登録し、
`.github/workflows/deploy.yml` のビルド手順に `env:` として渡します。

⚠ **8月の公開時点では、これをやらないでおくのがおすすめです。**
未登録なら投稿画面は「準備中」と出ます。イベント告知を優先し、
投稿機能は運用の準備（部長への周知、掲載ポリシーの説明）が整ってから開けてください。

## 8. 動作を確かめる順番

| # | 確かめること | 期待する結果 |

| 1 | `/submit/` にログインせず行く | 「Googleでログイン」が出る |
