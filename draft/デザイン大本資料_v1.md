## 2. コンセプト

### コンセプト文

> **「妄想の目録（カタログ）」**
>
> 大学生の頭の中にしかなかったものが、部活になり、PJになり、イベントになり、作品になる。
> このサイトは、その**変換の記録を綴じた1冊**である。

### 3つの設計原理

**原理1：数が説得力である**
Vision「北大で**最も大量に**おもろいことが生まれる場所」を、文章ではなく**画面上の物量**で証明する。
部活・PJ・イベントのタグを大量に、意図的に不揃いに配置する。項目が増えるほど画面が賑やかになる構造にする。

> ▸ なぜ：nexusmag.eu がカテゴリのピルを塗り／反転を混ぜてY座標をばらして置いていた（`screenshots/nexusmag_02_tags_filter.jpg`）。この手法は、**要素が増えることが劣化ではなく強化になる**という珍しい性質を持つ。学生団体は活動が増え続けるので、この性質と噛み合う。

**原理2：静けさが作品を立たせる**
作品集とPJページは、逆に**極限まで引く**。装飾ゼロ、余白最大、色は墨と生成りだけ。

> ▸ なぜ：エディトリアル事例70件の法則5（背景は白か生成りが多数派）。理由は「学生の作品は色も雰囲気もバラバラだから、サイト側が主張すると全部が濁る」。武蔵野美術大学の卒業制作作品集も**黒と白の2色のみ**で構成されていた（実測：黒975箇所・白34箇所）。

**原理3：引き算で品格をつくる**
書体4種・色4色・角丸1種・影ゼロ。これ以上は増やさない。

> ▸ なぜ：参考3サイトと事例70件に共通して、**枠線・影を使わず地の色を変えて面を分けている**。`box-shadow` は本サイトでは全面禁止とする。

## 3. サイト構成と、ページごとの性格

### タブ構成（並び順）

```
作品集    イベント    部活    PJ    団体紹介
WORKS     EVENT      CLUB    PJ    ABOUT
```

> ▸ なぜこの順：最優先読者はスポンサー。彼らが最初に知りたいのは「何を生み出しているか（＝成果物）」であり、組織図ではない。作品集を先頭に置き、団体紹介を最後に置く。
> 一方で新入生は「どんな活動があるか」から入るため、**イベント／部活／PJ を中央に3つ並べて対等に見せる**（基本情報の3本柱と一致）。

### 二層構造の割り当て

| ページ | 層 | 地の色 | アクセント量 | 動きの量 | ねらい |
|---|---|---|---|---|---|
| **トップ** | 妄想 | 生成り → スクロールで墨に反転 | 多 | 多 | 3秒で「本気の団体だ」と伝える |
| **団体紹介** | 妄想 | **墨** | 中 | 中 | 新聞紙面。密度＝信頼感 |
| **イベント** | 中間 | 生成り | 中 | 小 | 一覧性 |
| **部活** | 妄想 | 生成り | **最大** | 中 | 部活の数＝賑やかさ |
| **作品集** | 静謐 | 生成り／白 | **最小** | 最小 | 作品を邪魔しない |
| **PJ** | 静謐 | 生成り | 小 | 最小 | 読ませる |

⚠ **層の切り替えは「地の色の反転」で表現する。** 別の装飾を足さない。

## 4. デザイントークン

### 4-1. 色

```css
:root {
  /* ── ベース ───────────────────────────── */
  --ink:        #0E0E0E;  /* 墨。主要テキスト／反転時の地 */
  --paper:      #F4F1EA;  /* 生成り。基本の地 */
  --paper-card: #E8E5DE;  /* 紙灰。カードの地（罫線の代わり） */
  --white:      #FFFFFF;  /* 作品集のみ。作品の色を正しく見せる */

  /* ── アクセント（朱）────────────────────── */
  --shu:        #E8402A;  /* 面・大見出し用 */
  --shu-on-light: #C4321F;/* 生成り地の小さい文字用（4.87 AA）*/
  --shu-on-dark:  #FF6B54;/* 墨地の小さい文字用（6.88 AA）*/

  /* ── 補助テキスト ────────────────────── */
  --sub-on-light: #6B6862;/* 生成り地のキャプション（4.92 AA）*/
  --sub-on-dark:  #B8B3A8;/* 墨地のキャプション（9.24 AAA）*/
}
```

#### コントラスト実測表（WCAG 2.1 相対輝度式で自前計算）

| 文字色 | 背景色 | 比率 | 判定 | 用途 |
|---|---|---|---|---|
| `--ink` | `--paper` | **17.11** | AAA | 本文 |
| `--ink` | `--white` | **19.30** | AAA | 作品集の本文 |
| `--paper` | `--ink` | **17.11** | AAA | 反転時の本文 |
| `--ink` | `--shu` | **4.78** | AA | **朱の面＋墨文字（ピル・タグ）** |
| `--shu` | `--ink` | **4.78** | AA | 墨地の朱文字（本文可） |
| `--shu-on-light` | `--paper` | **4.87** | AA | **生成り地のリンク・小さい朱文字** |
| `--shu-on-dark` | `--ink` | **6.88** | AA | 墨地の小さい朱文字 |
| `--sub-on-light` | `--paper` | **4.92** | AA | キャプション・日付 |
| `--sub-on-dark` | `--ink` | **9.24** | AAA | 反転時のキャプション |
| `--shu` | `--paper` | 3.58 | 大文字のみ | **24px以上 or 太字18.7px以上に限定** |
| `--white` | `--shu` | 4.04 | 大文字のみ | ⚠ 朱地に白の小文字は使わない |

⚠ **絶対に守るルール**
1. **朱を生成り地の本文サイズに使わない**（3.58）。使うなら `--shu-on-light`（4.87）に差し替える。
2. **朱地に白の小さい文字を置かない**（4.04）。朱の面には**墨**を載せる（4.78）。
3. `--paper` と `--paper-card` の差は **1.115** しかない。**これは「面を分けるための装飾」であって、境界そのものが意味を持つ場合（押せる／押せないの区別など）は、別の手がかり（余白・文字・下線）を必ず併用する。**

> ▸ なぜ朱か：日本の印刷文化における朱入れ・落款の色であり、日本語エディトリアルと相性がよい。かつ参考3サイト（ライム／マスタード／無彩色）のいずれにも似ない。
> ▸ なぜ蛍光色を「面」に使うか：参考3サイトすべてがそうしていた。nexusmag のライムは白地では 1.15 で読めないが、ピルの塗りとして使い黒文字を載せることで 14.67 を確保している。**アーティスティックさとアクセシビリティは、この一手で両立する。**

### 4-2. 書体

```css
:root {
  --font-display: "Oi", serif;
    /* 英語の極太レトロスラブ。大見出しのみ。日本語グリフなし */
  --font-sans: "Switzer", "Zen Kaku Gothic New",
               "Yu Gothic", YuGothic, "Hiragino Kaku Gothic ProN", sans-serif;
    /* 見出し・本文・UI。欧文→和文→OS標準の3段構え */
  --font-serif: "Instrument Serif", "Shippori Mincho",
                "Yu Mincho", YuMincho, serif;
    /* 引用・情緒的な言葉のみ */
  --font-mono: "Space Mono", "M PLUS 1 Code", monospace;
    /* 日付・番号・カテゴリラベル */
}
```

すべて **Google Fonts / Fontshare の無料書体**。フォント費用は 0 円。

> ▸ なぜ「欧文書体を先に書く」か：和文書体の欧文グリフは品質が低い。先頭に欧文書体を置くと、**英数字だけがその書体で表示される**。
> 武蔵野美術大学（`a-otf-futo-go-b101-pr6n, 游ゴシック, ...`）とJAGDA（`aktiv-grotesk, a-otf-gothic-bbb-pr6n, 游ゴシック体, ...`）の**両方がこの順序で書いていた**（実測）。日本の実務における標準手法。

> ▸ なぜモノスペースを入れるか：エディトリアル事例70件の分析で、複数書体を使うサイトの大半が **Sans ＋ Serif ＋ Mono の三点セット**だった（Follow the Money、Telescope、Art+Tech Report、The Defense Reformation など）。**モノスペースのラベルは「今のエディトリアル」の指紋**であり、日付や番号を組むだけで素人写真でも誌面に見える。

⚠ `Oi` と `Space Mono` は**日本語グリフを持たない**。日本語を流し込むとフォールバックが起きる。
→ **`--font-display` と `--font-mono` は、英数字・記号のみに使う。** これはコードレビューの確認項目にする。

#### ⚠ モック実装で判明した問題：明朝体の費用対効果（2026-08-09 追記）

`draft/mock_top_v1.html` を実装し、実際のフォント転送量を計測したところ、**`--font-serif`（Shippori Mincho）の割に合わなさ**が明らかになった。

| 計測項目 | 実測値 |
|---|---|
| Google Fonts の CSS（和文2書体・計3ウェイト） | 344,838 bytes（圧縮後 **89,260 bytes**）|
| 和文を Zen Kaku 2ウェイトのみに減らした場合の CSS | 圧縮後 **58,867 bytes** |
| **明朝を足すことによる CSS の増分** | **＋約 30KB** |
| モック内で明朝が必要とする日本語の異なり字数 | **わずか 49字** |
| そのために追加ダウンロードされる書体ファイル | 推定 150〜300KB |

つまり **49文字のために、CSS 30KB ＋ 書体 150〜300KB を支払っている。**

☐ **判断が必要。** 選択肢は3つ：
1. **このまま使う** — 引用の情緒は明朝でしか出ない。目標1.5MBには収まる。
2. **明朝をやめる** — 引用も `--font-sans` で組み、サイズ・字間・囲みで差をつける。**最も軽い。**
3. **サブセットしてセルフホストする** — MVV など**固定の文章**にだけ明朝を使い、その文字だけに絞ったフォントを自前で持つ（5〜15KB程度になる）。ただし**学生の投稿文には使えない**（どんな文字が来るか事前に分からないため）。

▸ 推奨は **3**。MVV・コンセプト文といった「変わらない言葉」だけが明朝であればコンセプト上も筋が通り、投稿コンテンツは `--font-sans` で統一される。ただし実装がひと手間増える。

⚠ **ウェイトは Regular(400) と Bold(700) の2つまで。**
→ ▸ なぜ：日本語Webフォントは Google Fonts が121スライスに分割配信するため、実測で**1ウェイトあたり約150〜300KB**（スライス平均9.8KB × 15〜30個）。2ウェイトで300〜600KB。3ウェイト目を足すと写真1枚分が丸ごと増える。

### 4-3. 余白・寸法

```css
:root {
  /* 8pxを基本単位とする */
  --sp-1: 0.5rem;   /*  8px */
  --sp-2: 1rem;     /* 16px */
  --sp-3: 1.5rem;   /* 24px */
  --sp-4: 2rem;     /* 32px */
  --sp-6: 3rem;     /* 48px */
  --sp-8: 4rem;     /* 64px */
  --sp-12: 6rem;    /* 96px */
  --sp-16: 8rem;    /* 128px */
  --sp-24: 12rem;   /* 192px  セクション間 */

  --radius: 24px;   /* 角丸は1種類だけ */
  --radius-pill: 999px;
  --frame: 8px;     /* 額装の外周 */

  --measure: 34em;  /* 本文1行の最大幅（日本語で約40〜45文字）*/
}
```

⚠ **`box-shadow` は使わない。** 面は色で分ける。
⚠ **角丸は `--radius` と `--radius-pill` の2種類のみ。** カードごとに変えない。

> ▸ なぜ `--measure: 34em` か：日本語は1行40〜45文字を超えると視線が戻る位置を見失う。欧文の「1行75文字」をそのまま持ち込まない。

## 5. タイポグラフィ規定

### 5-1. スケール

| 役割 | 書体 | サイズ（PC） | サイズ（SP） | weight | line-height | letter-spacing |
|---|---|---|---|---|---|---|
| ディスプレイ（英） | `--font-display` | 96–160px | 48–72px | 400 | **0.9** | −0.02em |
| H1（和） | `--font-sans` | 48px | 32px | 700 | **1.2** | **−0.02em** |
| H2（和） | `--font-sans` | 32px | 24px | 700 | **1.3** | −0.02em |
| H3（和） | `--font-sans` | 20px | 18px | 700 | **1.6** | 0.02em |
| 本文（和） | `--font-sans` | **17px** | **16px** | 400 | **1.9** | **0.08em** |
| 引用（和） | `--font-serif` | 24px | 20px | 400 | **2.0** | 0.06em |
| キャプション | `--font-sans` | 14px | 13px | 400 | 1.7 | 0.06em |
| ラベル（英・数） | `--font-mono` | 12px | 11px | 400 | 1.5 | **0.12em** |

> ▸ **なぜ日本語の本文が line-height 1.9 / letter-spacing 0.08em なのか（重要）**
> 参考にした欧文サイトは見出しの line-height が **1.0** だった（nexusmag 45px/45px、techyscouts 48px/48px）。
> **これを日本語にそのまま適用すると窒息する。**
> 日本のトップクラスのデザイン系サイトを実測すると、真逆の値が出た：
>
> | サイト | 対象 | line-height | letter-spacing |
> |---|---|---|---|
> | 武蔵野美術大学 卒業制作作品集 | 本文 | **2.00** | **0.10em** |
> | 同上 | 学科名 | **2.50** | 0.094em |
> | JAGDA | 本文 | **1.80** | **0.071em** |
> | 同上 | 記事見出し | **2.00** | 0.075em |
>
> **和文は「ゆったり組む」ことが品格になる。ただし大見出しだけは詰める**（漢字が並ぶと隙間が空いて見えるため）。
> この使い分けが日本語エディトリアルの核心であり、**欧文サイトを真似るだけでは絶対に到達できない部分**。

### 5-2. 必須のCSS設定

```css
html { lang: ja; }          /* 実際は <html lang="ja"> */

/* 約物の余白を詰める。見出しのみ */
h1, h2, h3, .display { font-feature-settings: "palt" 1; }

/* 日本語の文節で改行する（Chrome 119+／未対応でも害なし）*/
h1, h2, h3, .lead { word-break: auto-phrase; }

/* 禁則 */
body { line-break: strict; overflow-wrap: anywhere; }

/* 数字を等幅に */
.meta, time, .num { font-variant-numeric: tabular-nums; }
```

> ▸ `font-feature-settings: "palt" 1` は**日本語組版の質を最も安く上げる1行**。`Zen Kaku Gothic New` も `Shippori Mincho` も対応している。ただし**本文には適用しない**（詰まりすぎて読みにくくなる）。

### 5-3. 日本語での「強調」の手段

日本語にはイタリックがない。使える強調は以下に限る。

| 手段 | 実装 | 用途 |
|---|---|---|
| **囲み** | `border: 2px solid; border-radius: 999px; padding: .1em .6em;` | 見出しの一部を囲む |
| 朱の面 | `background: var(--shu); color: var(--ink);` | タグ・カテゴリ |
| サイズのジャンプ | 本文17px ↔ 見出し48px（約3倍） | 階層 |
| 縦組み | `writing-mode: vertical-rl;` | セクションの柱を1本だけ |
| モノスペース | `--font-mono` | 日付・番号 |

> ▸ **「囲み」は武蔵野美術大学のサイトが使っていた手法**（`妄想を ( 形にする )` のように一部だけ角丸線で囲む）。日本語エディトリアルの数少ない有効な武器で、実装は3行。本サイトでも積極的に使う。

⚠ **`<i>` / `font-style: italic` を日本語に使わない。** 和文書体にイタリックは無いため、ブラウザが機械的に傾ける「疑似イタリック」になり、品質が著しく落ちる。

## 6. レイアウト原則

### 6-1. 額装（フレーム）

ページ全体を墨の外周で囲み、内側の「紙」を角丸にする。

```css
body { background: var(--ink); padding: var(--frame); }
main { background: var(--paper); border-radius: var(--radius); min-height: calc(100svh - var(--frame)*2); }
```

> ▸ なぜ：nexusmag.eu の最も効果的な手法（`screenshots/nexusmag_01_hero_frame.jpg`）。
> **「ブラウザ窓の中にもう一つ紙面がある」**という構造が、コンセプト「妄想の目録＝1冊の本」を、装飾を足さずに表現する。
> 実装はCSS3行。**費用対効果が最も高い一手。**
> さらに、二層構造の「墨のページ（団体紹介）」では `main` の背景を墨にするだけで、額と紙面が一体化する演出になる。

### 6-2. グリッド

```css
.grid { display: grid; gap: var(--sp-6);
  grid-template-columns: repeat(12, 1fr); }
```
- PC：12カラム。作品グリッドは **3列**（4カラム分ずつ）。
- タブレット：2列。SP：1列。
- **意図的に崩す**：セクションによって開始カラムをずらす（例：あるセクションは2〜11、次は1〜8、次は5〜12）。

> ▸ なぜ：エディトリアル2026の共通項が「非対称」と「余白を構造として使う」こと。**グリッドを捨てるのではなく、グリッドの上で非対称にする**のが今の作法。空の1カラムは無駄ではなく読みの合図。

### 6-3. 繰り返し使う3つの型

**型A：ラベル／本文の2カラム**（部活一覧・PJ一覧・組織図・沿革）
```
┌────────┬──────────────────────────┐
│        │ 読書部                     │ 20px bold
│ ● 部活  │ 2024年設立 ／ 部員12名      │ 14px --sub
│ (縦組み)│                            │
│        │ すこやか部                  │
│        │ 2025年設立 ／ 部員8名        │
└────────┴──────────────────────────┘
   2/12          10/12
```
> ▸ blancavillalobos.com の `• Experience` の構造（`screenshots/blanca_02_experience_2col.jpg`）。
> 左のラベルだけ書体・向きを変えて対立させるだけで「雑誌の柱」になる。日本語では**縦組み**にするとさらに効く。

**型B：フルブリード行＋オーバーレイ・キャプション**（作品集トップ）
```
┌───────────────────────────────────────────┐
│ 豆腐ゲーム                          詳細を見る │ ← 3行固定
│ 豆腐ゲームPJ ／ 山田・佐藤                    │
│ 2026                                       │
│                                            │
│          （画像／動画が画面幅いっぱい）        │
└───────────────────────────────────────────┘
```
- キャプションは **`作品名 / 制作者・所属 / 年`** の3行固定。
- `position: sticky; top: 0; height: 100svh;` で行を重ねると、1件ずつ「めくる」体験になる。

> ▸ blancavillalobos.com の作品行（`screenshots/blanca_03_works_fullbleed.jpg`）。
> **カードを使わず、画像そのものをカードにする。** 枠・影・角丸が無い分、余白と情報密度だけで高級感が出る。
> **この3行フォーマットが、そのまま投稿データのスキーマになる**（第9章）。

**型C：散らしたピル群**（部活一覧・トップ）
```
        ( 読書部 )            ( 詩タイピングPJ )
( 料理部 )   ( すこやか部 )   ( 実験再現PJ )  ( ふらっと部 )
      ( 豆腐ゲームPJ )   ( 新歓イベント )
```
- 塗り（朱地×墨文字）と反転（墨地×朱文字）と線のみ（枠だけ）を**交互に混ぜる**。
- Y座標を意図的にばらす。

> ▸ nexusmag.eu のカテゴリ群（`screenshots/nexusmag_02_tags_filter.jpg`）。
> **原理1「数が説得力である」を実装する主役。** 部活・PJが増えるほど画面が埋まり、Vision が UI 自体で証明される。

### 6-4. 画像が無いときのフォールバック（⚠ 必須）

```
┌─────────┐   ┌─────────┐   ┌─────────┐
│  写真    │   │  写真    │   │ (--paper-card) │
│         │   │         │   │  詩タイピング  │  ← 名前だけ
└─────────┘   └─────────┘   └─────────┘
 料理部        読書部
```

> ▸ 武蔵野美術大学のサイトが実際にこの処理をしている（`screenshots/musabi_02_category_grid.jpg` の「造形学部 通信教育課程」「大学院 造形研究科」）。
> **運用上、決定的に重要。** 部活やPJによっては必ず「まだ良い写真がない」状態が発生する。
> **この分岐をデータ設計の段階で決めておく**（`cover` が空のとき `--paper-card` 地＋名前だけのブロックに切り替える）。穴が空いた見た目にならない。

### 6-5. 写真の品質差を吸収する処理

```css
/* 作品集以外（イベント・部活・PJ）のサムネイル */
.thumb { filter: grayscale(1) contrast(1.12); transition: filter .4s cubic-bezier(.16,1,.3,1); }
.thumb::after { content:""; position:absolute; inset:0;
  background: var(--shu); mix-blend-mode: multiply; opacity:.28; transition: opacity .4s; }
.card:hover .thumb { filter: none; }
.card:hover .thumb::after { opacity: 0; }
```

> ▸ nexusmag のサムネイルは全て加工済みだった。これは審美的な選択であると同時に、**素材の品質差を消す装置**。
> 学生がスマホで撮った写真は明るさも色も構図もバラバラ。**サイト側で一律に処理すれば、学生に画像編集を要求せずに統一感が出る。**
> ⚠ ただし**作品集ページには適用しない**。作品そのものの色を変えてはならない。

## 8. モーション規定

### 8-1. 原則

⚠ **凝った入場演出は使うが、コンテンツは最初から見えている状態にする。**

> ▸ なぜ：nexusmag.eu は**ナビゲート後3秒間まっ白**だった（実測。4秒待って初めて描画）。
> 本サイトの最優先読者はスポンサーであり、彼らは回遊せず1回見て判断する。**初回描画が遅いサイトは、それだけで機会を失う。**
> → フェードインは「既にレイアウトされた要素の `opacity` と `transform`」だけを動かす。`display:none` からのマウントは禁止。

### 8-2. 実装手段：CSSのみ（JSライブラリ不使用）

```css
@keyframes reveal { from { opacity:0; translate:0 2rem } to { opacity:1; translate:0 0 } }
.reveal { animation: reveal linear both;
  animation-timeline: view(); animation-range: entry 0% cover 30%; }
```
- `animation-timeline` は 2026年時点でクロスブラウザ対応（Chrome/Edge 115+, Firefox 132+, Safari 18+、対応率約84%）。
- 未対応ブラウザでは**アニメーションが効かないだけ**でコンテンツは表示される（安全に劣化する）。
- ページ遷移は View Transitions API（`@view-transition { navigation: auto; }`）。

> ▸ なぜGSAP等を使わないか：**引き継ぎコスト。** 代表の任期は1年。GSAPのタイムラインを読める後輩がいる保証はない。CSSだけで書いてあれば、引き継ぎコストが桁違いに低い。
> ☐ 対応率は出典（CSSAWWWARDS / Frontend Horizon）の記述であり未検証。**実装前に caniuse で再確認する。**

### 8-3. タイミング

| 用途 | duration | easing |
|---|---|---|
| ホバー（色・下線） | 160ms | `ease-out` |
| 要素の出現 | 500ms | `cubic-bezier(.16,1,.3,1)` |
| ページ遷移 | 400ms | `cubic-bezier(.65,0,.35,1)` |

> ▸ `cubic-bezier(.16,1,.3,1)`（expo out）は「最初に速く、最後に長く減速する」曲線。**アーティスティック系サイトの上質さの多くは、色でも書体でもなくこの曲線に由来する。**

### 8-4. 制約

⚠ **1画面に同時に動く要素は3つまで。** それ以上は「賑やか」ではなく「安っぽい」になる。
⚠ **自動再生のカルーセルを使わない。**（武蔵野美術大学のサイトはこれを使っており、見たい画像が消えてしまう）
⚠ `prefers-reduced-motion: reduce` に必ず対応する。

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration:.01ms !important; animation-iteration-count:1 !important;
    transition-duration:.01ms !important; scroll-behavior:auto !important;
  }
}
```

## 9. データ設計（Next.js／将来の投稿機能を見据えて）

### 9-1. 共通スキーマ

型Bのキャプション3行（`作品名 / 制作者・所属 / 年`）が、そのままスキーマの骨格になる。

```ts
type Work = {
  slug: string;
  title: string;              // 作品名
  authors: string[];          // 制作者
  belongsTo: {                // 所属（部活 or PJ or イベント）
    kind: "club" | "project" | "event";
    slug: string;
  };
  year: number;
  publishedAt: string;        // YYYY-MM-DD
  cover?: ImageRef;           // ⚠ 空を許容 → フォールバック（6-4）
  images: ImageRef[];
  body: string;               // 本文（Markdown）
  tags: string[];
};

type Club = { slug; name; foundedYear; leader?; memberCount?; cover?; body; };
type Project = { slug; name; purpose; period; members: string[]; status; cover?; body; };
type Event = { slug; name; date; organizer; audience?; cover?; body; };
```

⚠ **`cover` は必ず optional にする。** 6-4のフォールバックを機能させるため。
⚠ **`memberCount` などの数値も optional。** 分からない数字を 0 で埋めない（CLAUDE.md 3-4）。

### 9-2. 段階的な拡張パス

| 段階 | データの置き場 | 誰が更新するか |
|---|---|---|
| **第1版（今）** | リポジトリ内の Markdown ＋ 画像 | あなた／Claude Code |
| 第2版 | 同上（＋Googleフォームで学生から受け取る） | 運営部が転記 |
| **第3版（1年以内）** | DB（Supabase等）＋ 認証＋投稿画面 | **学生本人** |

> ▸ **スキーマを最初から第3版の形で定義しておけば、置き場を差し替えるだけで移行できる。**
> 逆に、第1版でスキーマを雑に作ると、第3版で作り直しになる。**今いちばん重要な意思決定はここ。**

### 9-3. 技術構成

- **Next.js（App Router）**＋TypeScript
- 第1版：`generateStaticParams` による静的生成
- 画像：`next/image`（WebP/AVIF自動変換・srcset・CLS防止）
- スタイル：CSS Modules ＋ CSS変数（第4章のトークン）
  - ☐ Tailwind を使うかは未決。**本サイトはトークンが少なく型が固定されているため、素のCSSの方が引き継ぎやすい可能性がある。** 次の工程で判断する。
- ホスティング：☐ 未決。**Vercel の無料プラン（Hobby）は商用利用を認めていないため、スポンサーのロゴを掲載した時点でリスクになりうる。** Cloudflare Pages を候補として検討する（規約は変わりうるので実装時に最新を確認）。

> ▸ Next.js を選んだ理由は「1年以内に確実に投稿機能を作る」という決定（決定事項9）。**表示速度だけなら Astro が有利だが、認証・投稿画面・画像アップロードまで作るなら Next.js の方が総工数が小さい。**

## 11. この設計が依拠している10の事実

すべて `reference/design-research/` に一次データがある。

1. 蛍光アクセントは「面」に使い、上に墨を載せる。地の色に対する細字には使わない（04：朱は生成り地で3.58、墨文字を載せれば4.78）
2. 日本語は行間1.8〜2.0、字間0.07〜0.10em。ただし大見出しだけは詰める（03：武蔵野美大・JAGDAの実測）
3. `font-family` は「欧文書体 → 和文書体 → OS標準」の3段構え（07：日本の実務標準）
4. モノスペースをラベル・日付・番号に使う（02：事例70件の共通項）
5. 枠線・影を使わず、地の色で面を分ける（01・02：参考3サイトと事例70件に共通）
6. 写真は必ず加工を通し、撮影品質の差をサイト側で吸収する（04・06）
7. 画像が無いときのフォールバックをデータ設計の段階で決める（07：武蔵野美大の実装）
8. 凝った入場演出は使うが、コンテンツは最初から見えている（05・06：nexusmag は3秒間まっ白）
9. 日本の学生団体サイトには、デザイン面で参照に値する事例がほとんど存在しない（07：**ちゃんと作るだけで圧倒的に目立つ**）
10. 書体費用は0円で目標品質に到達できる（02・03：無料書体で全て賄える）
