# サイト運用 引継ぎ資料

作成日：2026-08-16
対象：北大心理ゼミ ウェブサイト（`output/website/`）を、別のセッション・別の担当者が
　　　迷わず安全に更新できるようにするための資料。

**この資料の使い方：** 新しいセッションでこのサイトを触るときは、まずこのファイル全体を読む。
次に `draft/ロードマップ.md`（意思決定の経緯）と `output/website/CLAUDE.md` 相当（無ければ
このファイルが代わりを果たす）を見る。個々のコードのコメントは「なぜ」を説明しているので、
触る前に必ず読む。

---

## 0. 3行で言うと

- サイトは **`output/website/` の Next.js を静的書き出しし、GitHub Pages で配信**している。`main` に push すると自動でビルド・検査・公開が走る（`.github/workflows/deploy.yml`）。
- コンテンツの正は `content/*.md`（Git）。**学生の投稿は Supabase に一旦溜まり、代表が `/review/` で承認すると、Edge Function が GitHub に自動コミットして** `content/*.md` に反映される（投稿機能＝フェーズ6）。
- **検査（`npm run check`）を通らないコードは push しない。** 検査は「参考サイトが実際に失敗した点」を機械的に潰す仕組みで、ここを軽視すると必ず同じ失敗を繰り返す。

```
  │    └─ private.*            … 権限判定の関数（REST から直接呼べない場所に置いてある）
  └─ Storage: submissions バケット（非公開）… アップロードされた写真の一時置き場
   │
   ▼ 代表が /review/ で「公開する」を押す
Edge Function `publish` (supabase/functions/publish/)
   │  GitHub Data API で 1 コミット
   ▼
GitHub リポジトリ jinkinokino5-max/shinri-zemi（このプロジェクトそのもの）
   │  content/<種類>/<slug>.md ＋ public/photos/… を書き込む
   │  push で GitHub Actions が起動
   ▼
.github/workflows/deploy.yml
   │  npm run build（静的書き出し）→ npm run check（落ちたら停止）
   ▼
GitHub Pages … https://jinkinokino5-max.github.io/shinri-zemi/
```

**この図で最も大事な一文：** 公開済みコンテンツの「正」はいつも Git であって、Supabase ではない。
Supabase が全データを失っても、サイトは1文字も変わらない。Supabase にあるのは「まだ承認されていない提案」だけである。

## 4. 投稿機能（フェーズ6）を触るときに、特に注意すること

### 4-1. 「フロントの型」と「DB」と「Edge Function」は3か所同時に直す

投稿の項目を1つ増やす／変えるだけでも、次の**4か所**が食い違うと壊れる。

1. `output/website/lib/schema.ts` … 公開後の Markdown の正しい形（Zod）
2. `output/website/lib/submission/fields.ts` … 投稿フォームの項目定義（1と鏡になっていること）
3. `output/website/lib/submission/published.ts` … 「いま公開されているもの」を編集画面の初期値にする変換（2と同じキー名であること）
4. `output/website/supabase/functions/publish/to-markdown.ts` … 承認された投稿を実際に Markdown へ組み立てる処理（1のスキーマを満たす出力を作ること）

**変更後は必ず** `npm run check:publish`（`scripts/check-publish-markdown.mjs`）を実行する。
これは `to-markdown.ts` の出力を実際に `gray-matter` で読み、`lib/schema.ts` の Zod に通す往復テストで、
「承認したのにビルドが落ちる」という一番発見しづらい事故を、代表が押す前に潰すための仕組み。

### 4-2. Edge Function はコードを直しただけでは反映されない（重要）

`supabase/functions/publish/` の中身を編集しても、**Supabase 側にデプロイし直さない限り、
本番で動いているのは古いコードのまま**である。

**2026-08-16、これが実際に起きていたことを確認した。** `photos`（写真1本の並び）・`focus`（切り抜き位置）・
`delete`（削除提案）の機能がリポジトリには入っていたが、デプロイされていた Edge Function（v6）は
それより前のバージョンで、`data.photos` を認識しなかった。その結果、**「新しい写真を足さずに
既存の写真だけを維持する」更新提案を承認すると、表紙が黙って消える**という実害のあるバグが
本番で有効な状態だった。v7 として再デプロイして解消した。

**デプロイの方法は2つある。**

| 方法 | いつ使うか |
|---|---|
| Supabase MCP の `deploy_edge_function` | このセッションでコードを直したその場で。`project_id: pijlevaclmlhadwraapw`、`name: "publish"`、`entrypoint_path: "index.ts"`、`verify_jwt: true`、`files` に `index.ts` と `to-markdown.ts` の中身を渡す |
| `npx supabase functions deploy publish`（要ログイン・リンク） | ローカルCLIから。`draft/フェーズ6_セットアップ手順.md` 5-3 に手順あり |

**⚠ ルール：`supabase/functions/publish/*.ts` を編集したら、その場でどちらかの方法でデプロイし、
`mcp__claude_ai_Supabase__get_edge_function` で中身を取得して差分が無いことまで確認する。
「コミットした」で終わらせない。**

### 4-3. DB のマイグレーションは Supabase MCP の `apply_migration` で直接適用する

`supabase/migrations/*.sql` は**参照用のソースであって、勝手には流れない**。新しいマイグレーションを
書いたら、`mcp__claude_ai_Supabase__apply_migration`（`project_id: pijlevaclmlhadwraapw`）で
実際に流し、`get_advisors`（`type: "security"`）でセキュリティ検査が0件のままであることを確認する。

過去に実際に踏んだ罠：

- **配列の副問い合わせは `= any (select …)` と書けない。** `text = text[]` の型エラーで関数の作成時点で落ちる。`exists (select 1 from … where slug = any(配列カラム))` の形にする（`0001` の `private.may_submit` を参照）
- **権限判定用の関数を `public` スキーマに置くと、REST API から誰でも直接呼べてしまう。** `private` スキーマへ置き、`grant usage on schema private to authenticated, anon;` だけを与える（`0002_private_helpers.sql` 参照）

### 4-4. Google OAuth の「同意したのに戻ってきてしまう」症状

原因はほぼ常に **Supabase 側に登録した Client Secret の誤り**。ダッシュボードのログ（Auth Logs）に
`oauth2: "invalid_client" "The provided client secret is invalid."` が出る。詳しい切り分け方は
`draft/フェーズ6_セットアップ手順.md` の 3-C にある。Supabase MCP の `query_logs` でも
`source = 'auth_logs'` を見れば同じ情報が取れる。

## 6. よくやる作業の型

### 6-1. コンテンツ（部活・PJ・イベントの文章／写真）を直す

`output/website/content/<種類>/<slug>.md` を直接編集する。フロントマターの書き方は
既存ファイルのコメントに従う。編集後：

```bash
cd output/website
npm run build
npm run check
```

両方通ってから commit・push（**push は明示的な許可を得てから**。CLAUDE.md 4-2）。

**⚠ push の前に必ず `git fetch origin` して差分を見る。** 投稿機能（Edge Function）は
このリポジトリへ**このセッションを介さずに直接コミットする**。代表が `/review/` で
承認すれば、誰もこの PC の前にいなくても `main` は進む。ローカルの `main` が古いまま
push すると拒否されるか、最悪 `--force` の誘惑に駆られる。**force push はしない。**
`git fetch` → 中身を見る → 問題なければ `git merge --no-ff origin/main` で取り込んでから push する（10章の事故を参照）。

### 6-2. デザイン（CSS・レイアウト）を直す

`styles/tokens.css` に色・余白・書体の変数が集約されている。**新しい色を作らず、既存の変数を使う。**
コントラストを変える／新しい配色を使うときは、WCAG 2.1 相対輝度式で実測し、コメントに数値を残す
（`styles/base.css` の実測コメントの書式を踏襲する）。

### 6-3. 依存パッケージを追加する

`cd output/website && npm install <pkg>`。追加後は必ず `npm run build` で `output:'export'` と
矛盾しないか確認する（サーバー専用機能に依存するパッケージは使えない）。

### 6-4. 投稿機能に項目を1つ増やす

4章を参照。`schema.ts` → `fields.ts` → `published.ts` → `to-markdown.ts` の順に直し、
`npm run check:publish` を通し、Edge Function を再デプロイする。

### 6-5. 公開前に必ず実行する検査

```bash
cd output/website
npm run build          # 静的書き出し。作品0件でも通ることを確認（3章の不変条件2）
npm run check           # check:publish + check-custom-pages + check-content
```

本番相当（basePath 付き）で確認したいときは、PowerShell で：

```powershell
$env:BASE_PATH = "/shinri-zemi"
npm run build
node scripts/check-content.mjs
$env:BASE_PATH = ""
```

（Git Bash で `BASE_PATH=/shinri-zemi npm run build` を実行すると、環境によっては
Windows パスへ誤変換されることがある。実際に踏んだ。PowerShell を使うほうが安全）

## 7. デプロイフロー（誰が何を自動でやるか）

1. `main` に push
2. `.github/workflows/deploy.yml` が起動
   - `npm run build`（`BASE_PATH=/shinri-zemi` 付き）
   - `npm run check:publish`
   - `node scripts/check-custom-pages.mjs`
   - `node scripts/check-content.mjs`
   - どれか1つでも失敗したら、**その時点でデプロイされない**（壊れたまま公開されるのを防ぐ設計）
3. `actions/deploy-pages` が GitHub Pages へ公開

デプロイ状況の確認：

```bash
gh run list --repo jinkinokino5-max/shinri-zemi --limit 5
```

**⚠ Edge Function のデプロイはこのワークフローに含まれない。** GitHub 側の自動デプロイと
Supabase 側の Edge Function デプロイは完全に独立している。投稿機能を直したら、
4-2 の手順で別途デプロイすること。
