# アクセシビリティ・パフォーマンス：守るべき最低ライン

調査日：2026-08-09
「アーティスティック」と「読める・速い」は対立しない。参考3サイトを実測した結果、**破綻していたのは主にパフォーマンス側だった**ので、そこを構造的に防ぐための資料。

---

## 1. 参考サイトで実際に観測した問題

| サイト | 観測された問題 | 本件での回避策 |
|---|---|---|
| nexusmag.eu | **ナビゲート後3秒間まっ白**。4秒待って初めて描画された（実測） | 入場演出は「既に配置された要素の opacity/transform」だけを動かす。`display:none` からのマウントを避ける |
| nexusmag.eu | 見出しの `line-height` が **1.0** | 日本語では 1.15〜1.25（03資料参照） |
| blancavillalobos.com | **`<h1>`〜`<h4>` が1つも存在しなかった**（実測 `headings: []`） | 見出しは必ずセマンティックなタグで組む |
| blancavillalobos.com | 本文 **14px** | 日本語は16px以上 |
| selected.musabi.ac.jp | `<h1>` のテキストが空（画像で組んでいる） | ロゴを画像にするなら `alt` を入れ、`<h1>` にはテキストを置く |
| techyscouts.com | `<h1>` が無く `<h2>` が48px/weight400 で並列 | 1ページに `<h1>` を1つ。以降は階層を守る |

> **注釈：デザイン性の高いサイトほど見出しタグを捨てている、という傾向がはっきり出た。**
> 本件の最優先読者は**スポンサー・外部の大人**であり、彼らは検索でたどり着く可能性が高い。
> **見出しタグを正しく組むことは、本件では「配慮」ではなく「目的達成の手段」。**

## 2. アクセシビリティ・チェックリスト（実装時に必ず確認）

### 文字とコントラスト
- [ ] 本文は **16px以上**（日本語）
- [ ] 本文のコントラスト比 **4.5:1 以上** ／ 大見出し（24px以上 or 太字18.7px以上）は **3:1 以上**
- [ ] **蛍光アクセント（ライム）は面としてのみ使う。白地の細字に使わない**（04資料の実測表：白地のライムは 1.17 で読めない）
- [ ] ブラウザの文字サイズを200%にしても崩れない（`px` 固定の高さを避け、`rem`／`em` を使う）

### 構造
- [ ] 1ページに `<h1>` は1つ、階層を飛ばさない
- [ ] 画像に `alt`。**装飾画像は `alt=""`**（読み上げから除外）
- [ ] 作品画像の `alt` は「作品名／制作者」を入れる（＝SEOにも効く）
- [ ] キーボードだけで全ページを回れる。`:focus-visible` のスタイルを消さない
```css
:focus-visible { outline: 3px solid var(--accent); outline-offset: 2px; }
```
- [ ] リンクとボタンを使い分ける（`<div onclick>` を使わない）

### モーション
- [ ] `prefers-reduced-motion: reduce` に対応（05資料のスニペット）
- [ ] 自動再生のカルーセルを使わない（武蔵野美大サイトの弱点として指摘済み）
- [ ] 自動再生動画は `muted` + `playsinline`、再生停止の手段を用意

### 日本語固有
- [ ] `lang="ja"` を `<html>` に指定
- [ ] `font-feature-settings: "palt" 1` は**見出しのみ**（本文に適用すると読みにくくなる）
- [ ] ふりがなが必要な固有名詞には `<ruby>` を検討

## 3. パフォーマンス：本件で最も重い要素は「学生の写真」

書体（03資料の実測：日本語Webフォント2ウェイトで300〜600KB）よりも、**未加工の写真の方がはるかに重い**。
スマホで撮った写真は1枚 3〜8MB になることがあり、20枚並べば数十MBになる。**ここを仕組みで防がないと、運用開始後3ヶ月で確実に破綻する。**

### 対策（優先順）

**① ビルド時に自動最適化する（最重要）**
Astro の `astro:assets` / Next.js の `next/image` は、
- WebP / AVIF への自動変換
- `srcset` の自動生成（画面幅に応じて適切なサイズを配信）
- `width` / `height` の自動付与（**CLS＝レイアウトのガタつきを防ぐ**）

を自動で行う。**学生が巨大な写真をそのまま置いても、配信されるのは最適化後のもの**になる。
> **注釈：これは「学生に画像を圧縮してから入れてもらう」という運用ルールより、はるかに確実。**
> 人に依存するルールは必ず守られなくなる。仕組みで解決する。

**② 遅延読み込み**
```html
<img loading="lazy" decoding="async" ...>
```
ただし**ファーストビューの画像には付けない**（かえって遅くなる）。

**③ 目標値**
| 指標 | 目標 | 意味 |
|---|---|---|
| LCP | 2.5秒以内 | 最大要素が表示されるまで |
| CLS | 0.1未満 | 表示中にガタつかない |
| INP | 200ms以内 | 操作への反応 |
| 総転送量（初回・トップ） | **1.5MB以内** | 大学のWi-Fiや電車内でも見られる |

**④ フォント読み込み**
```html
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
```
- `font-display: swap` を必ず指定（Google Fonts のURLに `&display=swap` を付ける）
- ウェイトは2つまで（03資料の実測に基づく）
- **さらに軽くするなら、サブセット済みフォントをセルフホスト**する。日本語は `subset-font` や `fonttools` の `pyftsubset` で、実際に使う文字だけに絞れる。ただし**投稿型サイトでは将来どんな文字が来るか分からない**ため、本件では **Google Fonts の動的サブセット（unicode-range 121分割）に任せる方が安全**。

## 4. SEO：スポンサーに見つけてもらうために

最優先読者がスポンサー・外部の大人である以上、検索でたどり着けることは要件。

- [ ] 各ページに固有の `<title>` と `<meta name="description">`
- [ ] OGP画像（SNSでシェアされたときのカード）。**作品ページは作品画像をOGPにする**
- [ ] 構造化データ（JSON-LD）：団体は `Organization`、イベントは `Event`、作品は `CreativeWork`
- [ ] `sitemap.xml`（Astro なら `@astrojs/sitemap` で自動）
- [ ] 「北大 心理ゼミ」「北海道大学 学生団体」等での検索を想定した見出し文言

> **注釈：OGP画像を作品画像にすることは、SEOよりも「学生が友達に見せたくなる」目的に直結する。**
> LINEやInstagramのDMでURLを送ったとき、自分の作品がカードとして出る——これが投稿の動機になる。
> 目的1（自発的に投稿したくなる場）と目的2（スポンサー向け）が、この1点で両立する。
